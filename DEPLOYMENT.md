# Будущая публикация habit_tracker на Ubuntu 24.04

Статус: локальная подготовка, **не выполнено на VPS**. Шаблоны требуют проверки на настоящем Linux. Размещение пока не начинать: локальная чистая установка Windows подтверждена после диагностики TLS; проверка установки на Linux и остальные ограничения остаются, см. VERIFICATION.md. Новых продуктовых функций и целей нет.

## 1. Сначала обследовать сервер

На VPS работают Manager Tracker и робот ВК. До любого изменения нужно получить подтверждённые имена их служб, рабочие каталоги, порты и способ запуска. Не останавливать и не менять их. Не заменять общий nginx.conf или чужие сайты. Проверить свободные RAM/CPU/диск/inode/swap, текущую нагрузку, версии Python/Nginx/systemd, доступный пакетный менеджер, брандмауэр, сертификаты и способ их продления.

Будущие **диагностические**, не выполненные здесь команды:

```bash
free -h
uptime
df -h
df -i
ss -ltnp
systemctl list-units --type=service --state=running
nginx -v
sudo nginx -t
```

Полный nginx -T не выводить и не сохранять в рамках read-only обследования: он может раскрывать чувствительные настройки. Безопасный следующий этап и недостающие сведения подключения описаны в [VPS_AUDIT.md](VPS_AUDIT.md). Отдельно проверить, что порт 8017 свободен, пользователь habit_tracker и предлагаемые каталоги не заняты. Если порт занят, выбрать другой свободный и одинаково изменить службу и новый сайт; чужой процесс не завершать. Оценить запасы с учётом scrypt при входе и одновременной нагрузки других приложений. **Достаточность 1 CPU/1 ГБ RAM не подтверждена**; не вводить произвольные лимиты памяти и не менять swap без обследования.

Предварительный домен: `habits.gilinsky.ru`. Владелец должен подтвердить его, DNS A/AAAA, отсутствие конфликта с существующим сайтом и возможность выпуска сертификата. Если указан AAAA, IPv6 должен действительно работать; пример Nginx содержит IPv4-listen, IPv6 добавляется отдельно после проверки. Порты 80/443 обслуживает имеющийся Nginx; отдельный экземпляр Nginx не запускается.

## 2. Изоляция файлов и пользователя

Предлагаемая схема (только habit_tracker):

| Назначение | Путь / имя |
|---|---|
| Пользователь и группа службы | habit_tracker, без интерактивного входа |
| Версии кода и отдельное окружение каждой версии | /opt/habit_tracker/releases/RELEASE |
| Ссылка на выбранную версию | /opt/habit_tracker/current |
| Постоянная база, вне кода | /var/lib/habit_tracker/habit_tracker.sqlite3 |
| Закрытые копии | /var/backups/habit_tracker |
| Закрытое окружение службы | /etc/habit_tracker/habit_tracker.env |
| Служба | habit_tracker.service |
| Отдельный сайт Nginx | /etc/nginx/sites-available/habit_tracker |
| Предлагаемый порт, свобода не проверена | 127.0.0.1:8017 |

После проверки отсутствия конфликтов создать отдельного системного пользователя:

```bash
sudo useradd --system --user-group --home-dir /var/lib/habit_tracker --shell /usr/sbin/nologin habit_tracker
sudo install -d -o root -g habit_tracker -m 0750 /opt/habit_tracker /opt/habit_tracker/releases
sudo install -d -o habit_tracker -g habit_tracker -m 0700 /var/lib/habit_tracker
sudo install -d -o root -g root -m 0700 /var/backups/habit_tracker /etc/habit_tracker
```

Если пользователь/пути уже существуют — сначала проверить владельца и назначение, не менять автоматически. Код и окружение версий принадлежат администратору, служба имеет только чтение/исполнение; запись разрешена в постоянную папку данных. Не переносить Windows .venv, .dependencies, .qa-stage4, базы, копии, .env или кэш в release. Не запускать службу от root.

## 3. Подготовить одну новую версию

RELEASE — уникальный идентификатор проверенного набора исходников, например дата и номер версии; сохранить предыдущий release. Распаковать только исходники habit_tracker и requirements в новый каталог. В Ubuntu нужен Python 3.12 с venv/sqlite3; недостающие системные пакеты устанавливать лишь после обследования и отдельно согласованного размещения.

```bash
python3 -m venv /opt/habit_tracker/releases/RELEASE/.venv
/opt/habit_tracker/releases/RELEASE/.venv/bin/python -m pip install -r /opt/habit_tracker/releases/RELEASE/deploy/requirements-linux.txt
/opt/habit_tracker/releases/RELEASE/.venv/bin/python -m pip check
```

Команды выполняет администратор с правом записи в этот release, не пользователь веб-службы. `deploy/requirements-linux.txt` фиксирует Gunicorn 27.0.1 и использует общие зависимости. Установка и запуск этого файла на Linux ещё не проверены. До допуска публикации выполнить чистую установку и весь набор pytest на временной базе; тестовые зависимости — requirements-dev.txt в отдельном окружении проверки.

После установки закрытого окружения и проверки разрешений выбранная версия назначается ссылкой current. Не пересоздавать existing release и не размещать данные внутри него. Проверить, что /opt/habit_tracker/current/.venv/bin/gunicorn соответствует выбранному release.

## 4. Секреты, cookie и доверенный прокси

Создать `/etc/habit_tracker/habit_tracker.env` по `deploy/habit_tracker.env.example`, root:root, 0600. Случайный SECRET_KEY не короче 32 байт создаётся на сервере и сохраняется только в закрытом окружении; его не копировать в Git, команды запуска, историю оболочки или журналы. После обновлений сохранять тот же ключ. Пустой или состоящий из пробелов ключ в production запрещает запуск.

- APP_ENV=production: отладка выключена; cookie Secure, HttpOnly, SameSite=Lax.
- DATABASE_PATH=/var/lib/habit_tracker/habit_tracker.sqlite3: абсолютный постоянный путь.
- TRUST_PROXY_HEADERS=1: явно доверять ровно одному локальному прокси для адреса и схемы. По умолчанию 0. Включать только с loopback-bind и перезаписью заголовков в нашем Nginx. Доверия к X-Forwarded-Host/Port/Prefix нет.
- TRUSTED_HOSTS=habits.gilinsky.ru: проверка Host (при смене домена обновить).

Файл окружения имеет формат EnvironmentFile systemd, не исполняется как shell-скрипт. CLI миграции запускается с тем же окружением через transient systemd unit, чтобы не публиковать секрет и не давать service-user чтение root-файла.

## 5. Новая база или перенос существующей

Проверить происхождение выбранной базы. Не запускать init-db как шаг обычного запуска сервиса. Для новой базы — один раз init-db, для существующей — копия перед upgrade-db. Если нужна локальная пользовательская база, переносить согласованную копию через безопасный канал, не через Git. Источник и служба во время финального переноса не должны принимать новые записи.

После назначения current команда для **новой** базы:

```bash
sudo systemd-run --wait --pipe --collect --unit=habit_tracker-init --property=User=habit_tracker --property=Group=habit_tracker --property=UMask=0077 --property=WorkingDirectory=/opt/habit_tracker/current --property=EnvironmentFile=/etc/habit_tracker/habit_tracker.env /opt/habit_tracker/current/.venv/bin/python -m flask --app wsgi:app init-db
```

Для existing базы сначала резервная копия, затем тот же способ запуска с `--unit=habit_tracker-migrate` и `upgrade-db` вместо init-db. Запускать миграцию только после остановки **habit_tracker**, не чужих служб. Повторный upgrade-db безопасен для поддерживаемых схем, но произвольную схему вручную не исправляет.

## 6. Gunicorn и systemd

Шаблон `deploy/habit_tracker.service` устанавливается отдельным unit. Один worker (плюс master Gunicorn), sync, один поток; без reload/debug. Счётчики входа в памяти этого worker сбрасываются при перезапуске; несколько worker пока нельзя включать без пересмотра ограничения. Gunicorn слушает только 127.0.0.1, внешний доступ только через Nginx. systemd разрешает запись лишь в /var/lib/habit_tracker, секрет читает менеджер systemd перед сменой пользователя.

После сверки путей и окружения, только на этапе размещения:

```bash
sudo install -m 0644 /opt/habit_tracker/current/deploy/habit_tracker.service /etc/systemd/system/habit_tracker.service
sudo systemctl daemon-reload
sudo systemctl enable --now habit_tracker.service
sudo systemctl status habit_tracker.service
curl --fail -H 'Host: habits.gilinsky.ru' http://127.0.0.1:8017/health
```

/health подтверждает процесс, а не исправность базы. Проверить также вход и чтение данных. Журналы — `journalctl -u habit_tracker.service`; не включать логирование паролей, тел форм, cookie или окружения. Flask development server для публикации не используется.

## 7. Отдельный сайт Nginx и HTTPS

Сначала сохранить конфигурацию Nginx, убедиться в исправности существующих сайтов и nginx -t. Для первичного выпуска сертификата использовать только HTTP-шаблон `deploy/habit_tracker.nginx-bootstrap.conf`, отдельный файл sites-available/habit_tracker и ссылку в sites-enabled. Он обслуживает ACME challenge из /var/www/habit_tracker-acme, остальные запросы возвращают 503. Каталог webroot — root-owned, читаемый Nginx. **Не включать сразу SSL-шаблон с ещё не существующим сертификатом**. Не включать два шаблона одновременно.

Проверить DNS и доступ challenge снаружи, nginx -t, затем reload существующего Nginx. Для выпуска через уже установленный и проверенный Certbot:

```bash
sudo certbot certonly --webroot -w /var/www/habit_tracker-acme -d habits.gilinsky.ru
```

Не применять автоматическое переписывание чужих сайтов. После выпуска проверить реальные пути cert/key; заменить содержимое только нового сайта на `deploy/habit_tracker.nginx.conf`, выполнить nginx -t и затем `systemctl reload nginx`. Если проверка не прошла — не перезагружать конфигурацию. После reload проверить также Manager Tracker и робот ВК.

Nginx перезаписывает X-Forwarded-For реальным адресом соединения и X-Forwarded-Proto схемой, отбрасывает остальные forwarded-поля, передаёт Host. При внешнем CDN/дополнительном прокси этот шаблон нужно пересмотреть до включения. Запросы на 80 перенаправляются на HTTPS, ACME остаётся доступным. Не включать HSTS includeSubDomains для всего домена без отдельной проверки других сервисов.

Проверить настоящий HTTPS, цепочку сертификата, cookie, CSRF при POST, заголовки и автоматическое продление. Для webroot нужен проверенный deploy-hook, выполняющий nginx -t и reload только после успешного продления; существующие задания Certbot не заменять. Провести `certbot renew --dry-run` в согласованное время и убедиться, что проверка относится к ожидаемым сертификатам. Наличие и периодичность заданий продления — часть обследования сервера.

## 8. Согласованная копия SQLite

Скрипт `deploy/backup_sqlite.py` использует SQLite backup API, открывает исходник read-only, проверяет integrity_check и отказывается перезаписывать существующий файл. Он подходит для согласованной копии и при работающем SQLite; не копировать один живой .sqlite3 через cp без учёта journal/WAL. Нужны запас места и закрытые права на каталог копий.

```bash
sudo /opt/habit_tracker/current/.venv/bin/python /opt/habit_tracker/current/deploy/backup_sqlite.py /var/lib/habit_tracker/habit_tracker.sqlite3 /var/backups/habit_tracker/pre-update-UNIQUE.sqlite3
```

UNIQUE заменить уникальной датой/версией, не перезаписывать прежнюю копию. У копии права 0600; зашифрованную внешнюю копию и срок хранения согласовать отдельно. Регулярность/retention не настроены автоматически. Проверять восстановление на временном файле и сохранять вместе с копией номер соответствующей версии кода. Если скрипт аварийно завершился, оставшийся файл не считать исправной копией.

## 9. Обновление и откат

Обновление:

1. Подготовить новый release с новым окружением и тестами, не меняя current/данные; записать текущий release и контрольные суммы поставки.
2. Остановить только habit_tracker.service, дождаться завершения worker; не оставлять второй процесс с той же базой.
3. Создать и проверить pre-update копию SQLite через backup API, записать связь «копия — старый release — версия схемы».
4. Переключить current на новый release. Запустить upgrade-db через transient unit с прежним закрытым EnvironmentFile.
5. При успехе запустить только habit_tracker, проверить /health, вход, привычки, отметки, статистику, архив и чужой доступ. Проверить, что другие приложения работают как до обновления.
6. При ошибке не продолжать миграции вручную; выполнить откат к согласованной паре кода и базы.

Откат:

1. Остановить только habit_tracker, проверить отсутствие других писателей. Сохранить отдельную копию неудачного состояния через backup API.
2. Выбрать прежний release и **соответствующую pre-update копию**. Убедиться в integrity_check копии. Объяснить пользователю потерю записей после этой копии; не восстанавливать автоматически поверх более новых данных.
3. Восстановить базу через SQLite backup API при остановленном приложении (из проверенной копии в постоянный файл), а не поверх работающего процесса. Закрыть все соединения; SQLite сам обрабатывает journaling. Выполнять восстановление от habit_tracker из подготовленной закрытой копии, доступной этому пользователю, чтобы владелец базы/служебных файлов оставался правильным. Не удалять WAL/SHM вручную у работающего SQLite.
4. Переключить current на старый release, сохранить прежний SECRET_KEY, проверить права на постоянные данные и запустить habit_tracker. Не выполнять upgrade-db новой версии после восстановления старой схемы.
5. Повторить проверку входа и данных, убедиться в работе соседних приложений. Публично открыть приложение только после подтверждения.

На ранних схемах обратная миграция не предусмотрена, поэтому откат только к проверенной паре кода и копии базы. Предыдущие release и копии не удалять до успешной приёмки.

## 10. Что требуется для следующего этапа

Подтверждённые ОС/ресурсы/нагрузка и место под копии; способ доступа и права администратора; имена/порты/пути Manager Tracker и робота ВК; текущий Nginx и включённые сайты; свободный порт; подтверждение habits.gilinsky.ru, A/AAAA и управление DNS; текущие TLS/Certbot/renewal; источник переносимой базы; окно обслуживания, допустимая потеря данных при откате, хранение внешних копий. До этих сведений нельзя утверждать, что сервер подходит.

Основания шаблонов: [Gunicorn settings](https://gunicorn.org/reference/settings/), [Nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), [Python SQLite backup API](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), [Certbot webroot](https://certbot.eff.org/instructions?ws=nginx&os=pip). Эти документы не заменяют проверку шаблонов на Ubuntu 24.04.
