# Следующий этап: только чтение состояния VPS

Сейчас подключение не выполняется. Этот план не предусматривает установку пакетов, изменение файлов/конфигураций/DNS, reload/restart служб или запуск habit_tracker. Manager Tracker и робот ВК продолжают работать. Если для чтения не хватает прав — зафиксировать это, не менять права и не устанавливать инструменты.

## Что уже известно из проекта

Планируется Ubuntu 24.04, ориентир 1 CPU / 1 ГБ RAM; фактические ресурсы и нагрузка не проверены. На сервере работают Manager Tracker и робот ВК. Предварительный домен — habits.gilinsky.ru. Предлагаемый localhost-порт Gunicorn — 8017, его свобода не проверена. Это **не SSH-порт**, а домен приложения не является подтверждённым адресом SSH.

В проекте нет подтверждённых host/IP, SSH-пользователя, SSH-порта, bastion/jump-host или имени готового SSH-профиля. Подключаться по догадке нельзя.

## Сведения, которые нужны перед подключением

- Адрес SSH (IP/hostname) либо имя уже настроенного профиля; SSH-порт и имя пользователя.
- Нужен ли VPN или jump-host и доступен ли он сейчас. Настройки сети не меняются в рамках обследования.
- Способ аутентификации: уже загруженный ключ в SSH-agent или существующий локальный профиль/путь к ключу. **Пароль и содержимое закрытого ключа в чат не присылать.** Если потребуется пароль/подтверждение ключа, пользователь вводит его самостоятельно штатным способом.
- Ожидаемый отпечаток host key из доверенного источника/панели провайдера. Проверку host key не отключать и неизвестный ключ автоматически не принимать.
- Разрешены ли read-only sudo-команды; известные имена systemd-служб Manager Tracker/робота ВК и их домены (если известны). При отсутствии имён сначала определить по безопасному списку служб, без просмотра окружения и аргументов запуска.

После получения этих сведений и явного разрешения на следующий этап — одно подключение для чтения. Секреты и полные диагностические дампы не публикуются.

## Минимальные диагностические команды (ещё не выполнялись)

```bash
uname -sr
cat /etc/os-release
python3 --version
getconf _NPROCESSORS_ONLN
uptime
free -h
df -hT
df -i
ps -eo pid,comm,pcpu,pmem --sort=-pcpu
systemctl list-units --type=service --state=running --no-pager
ss -ltnp
nginx -v
systemctl list-timers --all '*certbot*' --no-pager
```

Не использовать `ps aux`, `/proc/*/environ`, `printenv`, `systemctl show` без списка свойств, `systemctl cat`, журналы с неизвестным содержимым или полные аргументы процессов: там могут быть токены и пароли. Из списка процессов достаточно имён, PID и процентов; из портов — адреса привязки, порты и PID. Для UDP при необходимости — ss -lunp. Для процессов/портов, скрытых без root, запросить только необходимое read-only sudo.

Для точно определённых служб (подставить подтверждённые имена, ничего не останавливая):

```bash
systemctl show CONFIRMED_UNIT --property=Id,ActiveState,SubState,MainPID,User,Group,MemoryCurrent,CPUUsageNSec --no-pager
```

Вычислить запас RAM/CPU/диска с учётом текущей нагрузки и будущих копий, без заключения «ресурсов достаточно» по одному снимку. Отметить, занят ли 8017, и не трогать занимающий его процесс.

## Nginx и сертификаты без раскрытия секретов

Определить версию, расположение конфигурации и включённых сайтов. **Не выводить сырой nginx -T и содержимое конфигураций в чат.** Вывод может содержать Authorization, токены и URL с учётными данными. Для отчёта разрешён только небольшой проверенный список: имена сайтов, listen/server_name, наличие TLS и сроки публичных сертификатов; значения proxy_set_header, auth-параметры, URL с credentials, пароли и ключи исключить.

Предыдущий DEPLOYMENT.md включал nginx -T как будущую диагностику: для этого этапа его полный вывод не используется. Конфигурацию при необходимости читать ограниченно и обрабатывать на сервере, выводить только проверенные нечувствительные поля. Не копировать полные конфиги локально и не сохранять дампы на сервере. Если безопасная фильтрация неоднозначна — остановиться и запросить у владельца только нужные сведения.

Не читать ssl_certificate_key. Для известного **публичного** PEM-сертификата можно выполнить:

```bash
openssl x509 -in CONFIRMED_PUBLIC_CERTIFICATE_PATH -noout -subject -issuer -dates -ext subjectAltName
```

Наличие Certbot/таймера не доказывает успешное продление. Не выполнять renew --dry-run, выдачу сертификата или другие ACME-запросы в read-only этапе. Не менять DNS и не проверять новые challenge-файлы. При необходимости узнать порядок продления у администратора без чтения .env и файлов credentials.
